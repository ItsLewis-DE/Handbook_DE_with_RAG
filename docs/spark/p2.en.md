In Spark, it is important to distinguish between a **Logical Join** and a **Physical Join Strategy**. Spark supports standard SQL join types such as `LEFT`, `RIGHT`, and `INNER`. At the physical execution layer, the **Catalyst Optimizer** chooses distributed algorithms, such as Broadcast Hash Join or Sort-Merge Join, to reduce network shuffle costs and optimize memory use. This article explains those physical join algorithms, then explores the role of RDDs, communication in PySpark, and memory management on the Driver and Executors.

## 1. Broadcast Hash Join

Data initially resides in partitions spread across Executors. For a **Broadcast Hash Join**, Spark collects the smaller table's partitions on the Driver to assemble the complete table. The Driver then builds a **hash table** from it.

Executors fetch and cache the hash table, then launch Tasks to scan each row in their partitions of the larger table. Each row is joined by looking up its key in the smaller table's hash table.

- **Advantages:** Eliminates shuffle costs. This is Spark's fastest join strategy.
- **Disadvantages:** Can exhaust Driver and Executor RAM if the table is too large; only suitable for joining a large table with a small one.

[![Broadcast Hash Join in Spark](../assets/images/spark/broadcast.png){ loading=lazy }](../assets/images/spark/broadcast.png){ title="View full-size image" }

## 2. Shuffle Hash Join

For a **Shuffle Hash Join**, data from both tables is shuffled across the network based on the hash of the join key. This brings rows with the same key into the same partition on an Executor.

Within each partition, Spark builds a **hash table** from the smaller table's data, then scans the larger table's rows and probes the hash table for matches.

This works much like Broadcast Hash Join, but starts with a shuffle and does not collect the smaller table's partitions on the Driver. The shuffle is needed when even the smaller table is too large to collect on the Driver without exhausting its RAM.

- **Advantages:** Faster than Sort-Merge Join because it does not require sorting.
- **Disadvantages:** Sensitive to **data skew** and **OOM (Out of Memory)** errors if a partition of the smaller table is still too large for the Executor's RAM.

[![Shuffle Hash Join in Spark](../assets/images/spark/shuffle_hash.png){ loading=lazy }](../assets/images/spark/shuffle_hash.png){ title="View full-size image" }

## 3. Sort-Merge Join (SMJ)

For a **Sort-Merge Join (SMJ)**, both tables are shuffled by join key to bring rows with matching keys into the same partition. The Executor then sorts both tables' data by join key.

The Executor scans the two sorted datasets together, using two read pointers to find rows with matching keys.

- **Advantages:** Handles very large datasets and supports spilling to disk when partitions exceed available RAM.
- **Disadvantages:** Incurs network shuffle costs, uses CPU for sorting, and is sensitive to data skew.

[![Sort-Merge Join in Spark](../assets/images/spark/sort_join.png){ loading=lazy .article-diagram--wide }](../assets/images/spark/sort_join.png){ title="View full-size image" }

## 4. Broadcast Nested Loop Join (BNLJ)

As with Broadcast Hash Join, the Driver collects the smaller table and broadcasts it to Executors. **Broadcast Nested Loop Join (BNLJ)** then uses two nested loops to compare each row of the larger table with each row of the smaller table.

BNLJ is particularly useful when there is no **equi-join key**, for example with conditions using `>`, `<`, `>=`, or `<=`. In these cases, Spark cannot use the usual Hash Join or Sort-Merge Join algorithms.

The nested loops can be illustrated as follows:

```python
# Illustrative logic inside an Executor Task
small_table = [row_1, row_2, ..., row_k]  # Fits entirely in the Executor's RAM

for large_row in large_table_partition:
    # Inner loop: scan the entire smaller table
    for small_row in small_table:
        if non_equi_condition(large_row, small_row):  # e.g. large_row.price > small_row.min_price
            emit_result(large_row, small_row)
```

[![Broadcast Nested Loop Join in Spark](../assets/images/spark/BNJT.png){ loading=lazy }](../assets/images/spark/BNJT.png){ title="View full-size image" }

## 5. Cartesian Product Join (Shuffle-and-Replicate Nested Loop Join)

**Cartesian Product Join**, also called **Shuffle-and-Replicate Nested Loop Join**, is the most expensive of these join strategies. It is used when there is no equi-join key and a table cannot be collected in RAM.

Spark pairs every partition of table A with every partition of table B, forming a Cartesian product. If table A has `P_A` partitions and table B has `P_B` partitions, Spark creates **`P_A × P_B` output partitions**.

Within each new partition, the Task scans the data using two nested loops, as in BNLJ.

## 6. RDDs and Their Role in Spark Execution

### What Is an RDD?

The **RDD (Resilient Distributed Dataset)** is Spark's core, lowest-level data abstraction. RDDs still underpin DataFrames: whether a program uses DataFrames, Datasets, or Spark SQL, Spark does not execute the DataFrame abstraction directly at the machine level.

- **DataFrames and SQL** provide a logical abstraction that lets users describe data as tables and columns. When an Action is called, the Catalyst Optimizer optimizes the query logic and produces a Physical Plan. This is then translated into a sequence or tree of RDDs, which the DAGScheduler uses to divide the work into Stages and Tasks.
- **Executors** perform computations through RDD methods.

### Execution Layers

```text
[User interface]          DataFrame API / Spark SQL / Datasets
                                         │
                                         ▼ (Catalyst Optimizer & Tungsten)
[Internal planning]       Logical Plan ──► Physical Plan
                                         │
                                         ▼ (Translated into internal RDDs)
[Core engine]             RDD Graph (FileScanRDD, ShuffledRowRDD, Lineage)
                                         │
                                         ▼ (DAGScheduler & TaskScheduler)
[Physical execution]      Stages ──► Tasks ──► Executor CPU/RAM
```

### RDD Fault Tolerance

**Fault tolerance** is a key feature of RDDs. When an Action is called, the Physical Plan is translated into an RDD tree. If a worker node fails, Spark can use this tree to recompute lost partitions on healthy worker nodes instead of abandoning the entire Job.

## 7. How PySpark Processes Communicate

Apache Spark supports languages including Scala, Java, Python, and R. **PySpark** is Spark's Python API, allowing users to write data processing programs in Python and run them on Spark. To work effectively with Spark, data engineers need to understand both PySpark code and the mechanisms behind it, especially how Python communicates with the Spark engine.

This section explains PySpark's internal communication on the **Driver** and **worker nodes**, including how Python calls reach the JVM for Spark to process.

### Why Does PySpark Need to Communicate with the Spark Engine?

PySpark provides a Python API, while Spark's execution engine runs primarily on the **JVM**. PySpark therefore needs a way for the Python process and JVM to communicate so that the Spark engine can handle user commands.

The **JVM (Java Virtual Machine)** is the runtime environment for programs written in Java and related languages such as Scala.

### Communication on the Driver

Communication on the Driver uses a **two-process model**:

- **Python Driver Process (CPython):** A regular Python process, visible in Task Manager or Activity Monitor, that executes the user's Python code.
- **JVM Driver Process (Java/Scala Spark Driver):** A background Java process created when `SparkSession` is initialized from Python.

These processes communicate through **Py4J**. When Python code makes a Spark API call, Py4J forwards it to the JVM Driver, which returns information to the Python process.

[![Communication between the Python Driver and JVM Driver through Py4J](../assets/images/spark/driver.png){ loading=lazy }](../assets/images/spark/driver.png){ title="View full-size image" }

When an **Action** is called, the JVM Driver starts a Job on the cluster and receives results from Executors. The results are then passed to the Python process through a **local socket**.

### Communication on Worker Nodes

Communication on worker nodes also uses a **two-process model**:

- **JVM Executor:** A Spark application can have one or more JVM Executor processes on each worker node. They manage computation threads and cached data, and execute computations on the node's data.
- **Python Worker Process (CPython):** When a Task contains Python code, such as RDD `map`/`filter` functions, Python UDFs, or Pandas UDFs, the JVM Executor launches Python Worker processes to execute it.

[![Communication between a JVM Executor and Python Worker on a worker node](../assets/images/spark/worker.png){ loading=lazy }](../assets/images/spark/worker.png){ title="View full-size image" }

## 8. Driver Memory

### Memory Components

Driver memory has **two parts**:

- **JVM Heap (`spark.driver.memory`):** The main RAM allocation for the JVM Driver process. It holds data collected from Executors and data used for broadcasts.
- **Memory Overhead (`spark.driver.memoryOverhead` — Off-Heap / Native):** Defaults to `max(384 MB, 0.10 * driverMemory)`. It covers operating system overhead, the Python Driver process, and related memory needs.

[![Spark Driver memory components](../assets/images/spark/driver_mem.png){ loading=lazy }](../assets/images/spark/driver_mem.png){ title="View full-size image" }

### How Driver Memory Is Reclaimed

- **JVM Garbage Collector (GC):** Automatically identifies and reclaims heap memory occupied by data that is no longer in use.
- **ContextCleaner:** Performs background cleanup of resources associated with objects reclaimed by the GC.
- **Explicit cleanup:** Developers can also request memory cleanup directly.

## 9. Executor Memory

Executor memory has **three parts**: JVM Heap, Memory Overhead, and Managed Off-Heap Memory.

### JVM Heap (`spark.executor.memory`)

The **JVM Heap** is divided into three main regions:

#### Reserved Memory

**Reserved Memory** is a fixed **300 MB** portion of the JVM Heap that Spark excludes from the memory available to the Unified Memory Manager for Execution and Storage. This leaves room for internal Spark/JVM structures and other memory needs, reducing the risk of running out of memory because Spark uses the entire heap.

#### Unified Memory Pool

The **Unified Memory Pool** is a shared memory region calculated as follows:

```text
Unified Memory = (spark.executor.memory - 300 MB) × spark.memory.fraction
```

By default, **`spark.memory.fraction = 0.6`**, or 60% of the available heap.

This pool has **two subregions**:

- **Execution Memory:** Holds short-lived data and is released when a Task finishes. It is used for shuffle data and hash tables for joins such as Shuffle Hash Join.
- **Storage Memory:** Holds cached or persisted DataFrames/RDDs (`df.cache()`, `df.persist()`) and **Broadcast Variables**, such as the hash table used in Broadcast Hash Join.

The boundary between Execution and Storage is **dynamic**, with a default split of **0.5**. Either region can borrow unused space from the other. However, Execution can reclaim memory that Storage has borrowed, while Storage cannot take Execution memory that a Task is using.

#### User Memory

**User Memory** is calculated as follows:

```text
User Memory = (spark.executor.memory - 300 MB) × (1 - spark.memory.fraction)
```

This accounts for about **40% of the heap remaining after Reserved Memory is deducted** and supports user-defined code, such as **UDFs**.

### Memory Overhead

**Memory Overhead** is memory outside the JVM Heap. In PySpark, Python Worker memory also counts toward this region if **`spark.executor.pyspark.memory`** is not configured.

### Managed Off-Heap Memory

**Managed Off-Heap Memory** is an optional allocation outside the heap for **Project Tungsten**. It is not managed by the JVM Garbage Collector, avoiding GC pauses for this memory when processing large datasets.
